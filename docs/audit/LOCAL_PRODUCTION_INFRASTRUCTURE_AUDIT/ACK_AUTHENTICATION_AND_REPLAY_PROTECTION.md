# NEXA — ACK Authentication & Replay Protection Specification

**Status:** IMPLEMENTED & VERIFIED  
**Version:** 1.0  
**Scope:** Cryptographic Signatures, Anti-Spoofing, Replay Defenses & Idempotency Guarantees  

---

## 1. Threat Model & Security Objectives

In a multi-transport and peer-to-peer mesh environment, acknowledgment packets are exposed to several active attack vectors:
1. **ACK Spoofing:** A rogue participant or intermediate mule attempts to fabricate a Delivery ACK to trick the sender into believing an undelivered message was received.
2. **Queue Hijacking / Premature Deletion:** An attacker injects a forged Delivery ACK to the Cloud Gateway to purge a legitimate recipient's pending offline messages.
3. **ACK Type Confusion:** An attacker forwards a Custody ACK disguised as a Delivery ACK (or vice versa) to manipulate queue or delivery states.
4. **Replay & Duplication:** An eavesdropper re-broadcasts previously captured ACKs to trigger redundant database writes or desynchronize state machines.

## 2. Cryptographic Authentication Architecture

All acknowledgments in NEXA are cryptographically bound to the acknowledging node's authoritative Ed25519 identity key.

### 2.1 Canonical Digest Construction (`AckDigestHelper.kt`)

Signatures are computed over a fixed-length SHA-256 digest of canonically structured domain-separated fields to prevent length extension, field concatenation ambiguity, and cross-type attacks:

#### Delivery ACK Canonical Digest
$$\text{Digest}_{\text{delivery}} = \text{SHA-256}\Big(\text{"NEXA\_DELIVERY\_ACK\_V1"} \mathbin{\Vert} \text{OriginalPacketID} \mathbin{\Vert} \text{Status} \mathbin{\Vert} \text{RecipientNxID} \mathbin{\Vert} \text{DeviceID} \mathbin{\Vert} \text{Timestamp}\Big)$$

#### Custody ACK Canonical Digest
$$\text{Digest}_{\text{custody}} = \text{SHA-256}\Big(\text{"NEXA\_CUSTODY\_ACK\_V1"} \mathbin{\Vert} \text{OriginalPacketID} \mathbin{\Vert} \text{CustodianNxID} \mathbin{\Vert} \text{Status} \mathbin{\Vert} \text{Timestamp}\Big)$$

### 2.2 Signature Generation & Verification
- **Signing (`Ed25519Signer.sign`):** Generated by the recipient or relay node using its local Ed25519 private identity key held in secure storage.
- **Verification (`Ed25519Signer.verify`):** Verified by the receiving node using the acknowledging party's verified public key stored in the local contact book or PostgreSQL identity registry.

```kotlin
val digest = AckDigestHelper.computeDeliveryAckDigest(
    originalPacketId = ack.originalPacketId,
    status = ack.status,
    recipientNxId = ack.recipientNxId,
    deviceId = ack.deviceId,
    timestamp = ack.timestamp
)
if (!Ed25519Signer.verify(digest, ack.signature, hexToBytes(contact.publicKeyHex))) {
    Log.e(TAG, "SECURITY REJECTION: Delivery ACK signature verification failed from ${packet.senderNxId}")
    return false
}
```

## 3. Anti-Spoofing & Validation Matrix

| Layer | Validation Check | Action on Failure | Attack Prevented |
| :--- | :--- | :--- | :--- |
| **Android Ingestion** | Target message exists in outbox | Silent drop (`return false`) | Phantom ACK injection |
| **Android Ingestion** | `packet.SenderNxId == message.RecipientNxId` | Security log & drop | Mismatched recipient spoofing |
| **Android Ingestion** | Ed25519 digital signature valid | Security log & drop | Forged signature / tampering |
| **Cloud Gateway** | Session authenticated (`sender.Authenticated`) | Log warning & drop | Unauthenticated queue purge |
| **Cloud Gateway** | `sender.NxId == packet.SenderNxId` | Log warning & drop | Cross-account queue deletion |
| **Cloud Gateway** | `packet.Type == PACKET_ACK` (Strict Type Separation) | Routed in RAM only | Type confusion (Custody ACK purging Redis) |

## 4. Idempotency & Replay Protection Guarantees

Because mesh protocols and multi-path networks often transmit identical packets over multiple routes simultaneously, all ACK processing is strictly idempotent:

### 4.1 Delivery ACK Idempotency
- When an already-delivered message receives a duplicate `PACKET_ACK(ACK_DEVICE_DELIVERED)`:
  - Database status remains `DELIVERED`.
  - No new user notification or unread counter is triggered.
  - Return code is `true` (idempotent success).

### 4.2 Custody ACK Idempotency
- When a sender receives duplicate `PACKET_CUSTODY_ACK(CUSTODY_ACCEPTED)` packets from the same or different relays:
  - If status is `CREATED`, `PENDING`, or `QUEUED`, it updates to `RELAYED`.
  - If status is already `RELAYED`, the update is a no-op and status remains `RELAYED`.
  - If status has already advanced to `DELIVERED` or `READ`, the Custody ACK **never downgrades the status back to `RELAYED`**.

### 4.3 Redis Queue Reconciliation Idempotency
- The Cloud Gateway calls `h.buffer.Acknowledge(ctx, recipientNxId, packetId)`.
- If the packet was already acknowledged by another device or a previous delivery path:
  - Redis returns `0` keys removed.
  - No error is raised.
  - Queue remains clean and in a consistent state.
