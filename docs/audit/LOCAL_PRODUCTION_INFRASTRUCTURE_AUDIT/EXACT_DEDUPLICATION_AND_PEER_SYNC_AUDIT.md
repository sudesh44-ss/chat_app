**Date:** 2026-11-09  
**Scope:** Cross-Transport Exact Deduplication, Persistent Transport Observations & Peer Anti-Entropy Synchronization  
**Status:** AUDIT COMPLETE — IMPLEMENTATION READY

## 1. Executive Summary

This audit assesses the current state of message deduplication, multi-transport ingestion, Bloom filter usage, and peer-to-peer state reconciliation across the NEXA Android client and Go backend.

NEXA delivers messages across three primary delivery mediums:
1. **Internet WebSocket (Cloud Gateway / Ephemeral Redis Queue)**
2. **Cellular Binary Data SMS (Port 8901)**
3. **Offline Mesh / DTN (Nearby Connections, BLE, Wi-Fi Direct, Wi-Fi Aware, Multi-Hop Data Mules)**

A single logical message generated by a user can arrive via multiple redundant transport paths simultaneously or sequentially (e.g., delivered via WebSocket, then relayed via Nearby mesh, or retried after reconnection).

The audit confirms that while Phase B/C cryptographic verification and Phase I gateway queue reconciliation are operating with 100% test pass rates and zero blockers, several architectural vulnerabilities and functional gaps currently exist in deduplication and synchronization:
- **Non-Atomic Ingestion Gate:** In Android, duplicate detection in `NexaUniversalTransportIngest` performs a non-atomic read (`messageDao.getMessageByPacketId`) before calling `ratchetDecrypt` and `insertMessageIfNotExists`. Concurrent delivery over two transports can cause concurrent ratchet decryption attempts, risking ratchet state corruption.
- **Bloom Filter False-Positive Drops:** `BloomDuplicateFilter` in `core/mesh/engine` returns `true` (duplicate found) on bitset matches and drops packets immediately without database verification, allowing false positives to permanently discard valid messages.
- **Missing Multi-Transport Observation History:** `MessageEntity` only records a single string `transportType`, losing history when subsequent transports deliver the same message.
- **Absence of Peer Anti-Entropy Synchronization:** When two contacts reconnect after temporary network partitions, there is no protocol to reconcile missing conversation messages within their authorized shared scope without manual resending.
- **Backend Redis Restart Reliance:** In the Go backend, message idempotency relies on ephemeral Redis `HEXISTS`. If Redis restarts or evicts keys after TTL, duplicate messages could be re-ingested without persistent conflict validation.

## 2. Android Client Audit

### 2.1 Database Schema & Message Entity
- **Entity:** `MessageEntity` in `app/src/main/java/com/nexa/app/data/local/entity/MessageEntity.kt`:
  - Primary Key: `packetId: String` (with unique index `index_messages_packetId`).
  - Fields: `conversationId`, `senderNxId`, `recipientNxId`, `plainTextContent`, `status`, `timestamp`, `isOutgoing`, `transportType`, `isPinned`, `pinnedExpiresAt`, `pinnedAt`.
  - Issue: Single `transportType` field records only the first transport. Subsequent deliveries over secondary transports (e.g. mesh delivery after cloud delivery) cannot record secondary transport observations.
- **DAO Operations:**
  - `MessageDao.insertMessage`: uses `OnConflictStrategy.REPLACE`.
  - `MessageDao.insertMessageIfNotExists`: uses `OnConflictStrategy.IGNORE`.
  - In `ChatRepositoryImpl.kt:666`, `insertMessage` (REPLACE) is called directly, which can overwrite existing state on duplicate delivery.

### 2.2 Ingestion Layer & Race Conditions
- **`NexaUniversalTransportIngest.kt`:**
  - Ingests wire packets and DTN envelopes across `INTERNET_WS`, `CELLULAR_DATA_SMS`, `OFFLINE_MESH`.
  - Deduplication check at line 167:
    ```kotlin
    val existing = messageDao.getMessageByPacketId(packet.packetId)
    if (existing != null) return true
    ```
  - Race Condition: Between checking `existing == null` and persisting the message, the pipeline performs Double Ratchet AEAD decryption (`doubleRatchetEngine.ratchetDecrypt`).
  - If two transports deliver the packet simultaneously (e.g. WebSocket and Nearby Connections within milliseconds), both threads see `existing == null` and execute `ratchetDecrypt` concurrently. The second decryption will fail MAC verification or consume ratchet keys improperly.

### 2.3 Bloom Filter Implementations
- **`BloomDuplicateFilter.kt` (4 KB sliding filter):**
  - Line 24: `if (bitSet.get(h1) && bitSet.get(h2) && bitSet.get(h3)) return true`
  - Critical Flaw: Acts as the final deduplication authority. If hash collisions produce a false positive, a valid new message is dropped without checking Room database.
- **`DtnBloomFilter.kt` (64-byte filter):**
  - Exchanged during Nearby Connections handshake to suppress redundant data mule replication.
  - While suitable as an optimization to filter held envelopes, false positives can cause peer B to skip sending an envelope that peer A actually lacks.

### 2.4 Multi-Device & Existing Sync State
- `DeviceSyncEntity` and `device_sync_log` exist in Room schema (Version 11 migration), with `DeviceSyncDao` storing sync entries per sequence number.
- `PACKET_DEVICE_SYNC` exists in wire protocol with `DeviceSyncPayload`.
- Current limitation: There is no peer-to-peer anti-entropy protocol for mutual contacts to exchange missing message inventories within their conversation.

## 3. Go Backend Audit

### 3.1 Cloud Gateway & Queue Idempotency
- **`backend/internal/queue/redis_buffer.go`:**
  - `Enqueue` executes `HEXISTS nexa:q:msg:<queueKey> <messageID>` before enqueuing to list.
  - Message ID extraction via `ExtractMessageID`: extracts wire packet ID (`pkt.PacketId`), 16-byte message UUID from NXDT envelope, or SHA-256 fallback.
- **Reliability Gap:**
  - Redis keys carry 24h ephemeral TTL. If a message is enqueued, delivered, and Redis is restarted or keys expire, a re-transmitted envelope could be accepted as new.
  - Conflict detection: If an attacker or misconfigured client transmits a packet with the same `packet_id` but conflicting sender or payload ciphertext, Redis `Enqueue` currently treats it as an idempotent no-op rather than flagging a security conflict.

### 3.2 Persistent Backend State (PostgreSQL)
- PostgreSQL schema (`backend/internal/database/migrations.go`) enforces identity, devices, sessions, connections, and prekey tables.
- Zero-Disk Privacy Policy: The backend does **not** store plaintext messages, maintaining zero message content exposure.
- Opportunity: A durable, server-side idempotency log (`message_idempotency` table) can track `(packet_id, sender_nx_id, recipient_nx_id, payload_sha256, created_at, expires_at)` without storing plaintext message text, ensuring exact deduplication across Redis restarts.

## 4. Protocol & Wire Envelope Audit

### 4.1 Message Identity Invariants
- `NexaWirePacket`:
  - `packet_id: String` (Field 1) — canonical, globally unique UUID assigned once at logical creation.
  - `sender_nx_id: String` (Field 3) — authenticated author.
  - `recipient_nx_id: String` (Field 4) — intended recipient.
  - `timestamp: Int64` (Field 5) — message creation time in epoch ms.
- `DtnEnvelope`:
  - Header magic: `NXDT` (bytes 0..3).
  - Protocol version: `0x01` (byte 4).
  - `message_uuid`: 16 bytes (bytes 20..35).
  - `sender_public_key`: 32 bytes (bytes 36..67).
  - `blind_token`: 16 bytes (bytes 68..83).
  - `auth_signature`: 64-byte Ed25519 signature (bytes 84..147) covering all authenticated fields.

### 4.2 Invariant Rules
1. **Immutability:** `packet_id` and `message_uuid` must never change during forwarding, relay custody, transport handoff, or peer synchronization.
2. **Text vs Identity:** A message with identical plaintext but different UUID is a separate logical message (never deduplicated).
3. **Conflict Detection:** If an incoming message matches an existing `packet_id` but differs in authenticated sender or ciphertext payload SHA-256 digest, it must be flagged as a security conflict.

## 5. Peer Synchronization Handshake Design

To reconcile missing messages between two authorized contacts without exposing unrelated data or plaintext:

### 5.1 Synchronization Scope
- Scope is strictly bounded to the shared conversation between authenticated parties:
  `conversationId = deriveConversationId(userA, userB)`
- Only messages where `senderNxId IN (userA, userB)` and `recipientNxId IN (userA, userB)` are eligible.
- Cross-conversation leakage is mathematically impossible.

### 5.2 Handshake Protocol (10-Step Anti-Entropy)
```
Peer A (Alice)                                                Peer B (Bob)
      │                                                             │
      ├────────────── 1. Authenticated Connection ─────────────────┤
      │               (Mutual Ed25519 Verified)                     │
      │                                                             │
      ├────────────── 2. SYNC_HELLO (Version, Capabilities) ────────►
      │                                                             │
      ◄────────────── 3. SYNC_HELLO_ACK (Compatible Version) ───────┤
      │                                                             │
      ├────────────── 4. SYNC_INVENTORY_REQ (Conversation, Cursor) ─►
      │                                                             │
      ◄────────────── 5. SYNC_INVENTORY_RESP (Bounded UUID List) ───┤
      │               (Compact list of packet IDs & timestamps)     │
      │                                                             │
      │ 6. Alice compares inventory against exact Room database      │
      │    (Identifies missing packet IDs: [msg_003, msg_007])       │
      │                                                             │
      ├────────────── 7. SYNC_PULL_REQ (Missing Packet IDs) ────────►
      │                                                             │
      ◄────────────── 8. SYNC_PULL_RESP (Sealed Encrypted Packets) ─┤
      │                                                             │
      │ 9. Alice ingests each via Universal Ingestion Pipeline      │
      │    (Exact Dedup Transaction -> Double Ratchet -> Room DB)   │
      │                                                             │
      ├────────────── 10. SYNC_COMPLETE_ACK (Reconciled IDs) ───────►
      │                                                             │
```

## 6. Implementation Roadmap

1. **Android Room Deduplication & Transport Observation Architecture:**
   - Create `MessageTransportEntity` and `MessageTransportDao` for `message_transport_observations`.
   - Add atomic transaction in `NexaUniversalTransportIngest` and `MessageDao` that combines deduplication lookup, conflict detection, and transport logging.
   - Guard against concurrent Double Ratchet decryption using atomic reservation.
2. **Bloom Filter Remediation:**
   - Modify `BloomDuplicateFilter` so positive bitset matches perform exact database checks rather than directly dropping packets.
3. **Backend Idempotency & Conflict Guard:**
   - Add `MessageIdempotency` store in Go backend with persistent hash/sender verification.
   - Reject conflicting message identities with protocol security error.
4. **Peer Synchronization Engine:**
   - Implement `PeerSyncManager` on Android supporting bounded batch reconciliation, pagination, and cursor tracking.
   - Wire packet extension for sync handshake (`PACKET_PEER_SYNC` or structured sync frames).
5. **Multi-Transport & Concurrency Tests:**
   - Android & Go tests for duplicate rejection, multi-transport delivery, conflict detection, restart survival, and peer synchronization.
